# 人机共情交互抑郁防范与健康促进系统

## 系统开发方案

项目标识：数字人系统 ServerRS　　目标软件版本：1.0

文档版本：2026 年 10 月整理版　　日期：2026 年 10 月 21 日

开发单位：合肥工业大学计算机与信息学院 A807 实验室

本方案以现有数字人系统为基础，完善用户端、服务端、管理后台与模型服务的协作。核心是将服务端生成的回复音频接入前端数字人，形成可阅读、可收听、可反馈的交互过程，并打通自评、活动建议及个人记录流程。

建设采用现有 Rust 服务端与 Vue 3 管理后台，沿用 MySQL、向量检索及模型适配能力。优先完善数字人音频链路、异常恢复和业务闭环，再完成权限验证、部署验证和验收资料。新增内容按迭代实施，不将建议项表述为现有功能。

# 1 建设目标与现状基线

### 1.1 建设目标

以数字人为交互主体，为用户提供支持性对话、心理健康自评和健康促进入口。服务端承担回复生成、语音生成和数据处理，用户端承担形象展示、音频播放、数字人驱动及交互反馈。建设成果应能复现一条完整的交流链路和一条自评活动链路，并具备可验证的权限与运行保障。

### 1.2 当前系统基线

| 能力域 | 当前情况 | 本轮建设重点 |
| --- | --- | --- |
| 用户端数字人 | 已有数字人 前端由返回音频驱动 | 补充播放状态 异常恢复与联调 |
| 对话语音 | 已有文字加音频接口及签名下载 | 配置核验 终端可达与播放验证 |
| 对话上下文 | 已有记忆 画像 摘要及 RAG | 核对数据控制和个性化行为 |
| 工具审批 | 已有暂停 待审批查询和恢复 | 完善界面 当前恢复仍为文字 |
| 自评与建议 | 已有量表 事务保存及轮询 | 完成用户端展示与状态反馈 |
| 管理后台 | 已有用户 风险 心理内容 音乐 | 统一现有入口与权限说明 |
| 部署 | 已有离线容器与直接托管方式 | 增加语音依赖和恢复验证 |

### 1.3 当前边界

现有量表配置为 PHQ-9、SDS、CES-D。风险检测在交流后异步审计，失败和未完成状态分别呈现。活动建议当前固定为呼吸练习和情绪日记，采用前台轮询，不能表述为按风险自动干预或关闭应用后推送。

Fresh Context 被启动层开关暂停；网页知识摄入保留实现并受自身配置控制，管理后台知识审核入口当前暂停。旧风险手工处置接口返回 410。QQ 智能秘书及其平台接入已经移出当前工程，不纳入本方案范围。

### 1.4 实施原则

复用已经实现的接口与分层结构，以可操作界面、明确异常状态和实际验证结果作为交付依据。前端补充遵循“服务端音频驱动数字人”的现有方向，渲染引擎和数字人资产沿用项目实际选型。

| F04 | 工具审批与恢复 | 展示批准 拒绝及刷新后待办恢复 | 必需 |
| F05 | 自评及记录 | 使用实际量表题目和服务端计分 | 必需 |

### 2.2 质量需求

同一终端同一交流区域只允许一条数字人回复音频播放；切换账号、离开页面和播放失败时收敛到明确状态。音频失败不得覆盖已经返回的文字。写入类操作超时后先查询记录，不默认重复提交。

登录、个人记录和管理数据应经过服务端权限检查。界面按用户理解显示“生成中”“等待确认”“播放失败”等状态，避免将网络错误展示为空数据。请求耗时、音频加载、资源占用及恢复时间应在目标设备实测并形成基线。

### 2.3 验收范围与暂缓范围

本轮覆盖账号、数字人交流、自评与建议、日记、知识、音乐、管理读取与必要维护、部署及文档。语音输入如需增加，应另行明确录音权限、识别服务和接口；当前核心请求字段为 text，不推定服务端已有 ASR。

逐音素口型时间轴、全双工实时语音、服务端视频生成、后台系统推送和自动人工干预作为独立后续需求，不作为当前能力承诺。数字人停播及打断界面可先实现，取消前端播放不代表服务端推理已取消。

# 3 总体架构与技术路线

### 3.1 总体架构

![系统总体架构](assets/system_architecture.png)

用户端与管理端通过 HTTP 接口进入 Rust 服务。认证与角色校验之后，由业务服务处理对话、量表、活动及资源。MySQL 保存业务事实；向量库用于语义检索；模型与语音服务通过适配器接入。数字人画面由用户端渲染，服务端不向前端直接发送数字人视频。

### 3.2 工程边界

| 组件 | 职责 | 依赖方向 |
| --- | --- | --- |
| agent-core | Graph Effect Checkpoint 暂停恢复 | 通用运行能力 |
| ai-core | LLM Embedding TTS 抽象协议 | Provider 中立接口 |
| digital-human | 对话 记忆 RAG 业务与持久化 | 使用上述两个基础包 |
| digital-human-server | Axum API 配置 启动装配及语音服务 | 装配通用能力与业务 |
| web/admin 与 web/sdk | 管理界面与 TypeScript 接入 | 调用服务端 HTTP 接口 |

继续沿用领域接口、应用服务、基础设施适配器和宿主装配的分层方式。新增数字人驱动逻辑放在用户端适配层；不要将特定渲染引擎对象带入服务端业务模型。

# 4 数字人音频交互方案

### 4.1 当前接口链路

![音频交互时序](assets/audio_sequence.png)

客户端发送 POST /api/v1/chat/messages-with-audio，携带 Bearer 凭证及 text、format、sampleRate、channels、sampleBits。建议首轮联调使用 wav、24000、1、16；voice 按部署白名单控制，默认可省略。

200 响应包含 conversationId、reply、toolCalls 和 audio。audio 提供 audioUrl、format、sampleRate、channels、sampleBits。先展示 reply，再获取音频并交给播放器和数字人驱动。当前是完成回复后返回音频地址的请求响应方式，不能按实时分片语音接口实现。

### 4.2 前端驱动职责

音频解码后向现有数字人组件提供音频数据或组件要求的输入，并以实际播放进度统一说话状态。推荐播放器与驱动共用同一音频来源和时钟，避免分别加载造成漂移。若现有驱动仅支持 PCM，则在客户端解码转换，或按接口支持规格请求；原始 PCM 需要调用方按参数构造播放数据，不能直接假定浏览器 Audio 元素可播。

当前响应没有 viseme 或音素时间标记。可沿用组件自带的音频驱动，或将音量包络驱动作为基础口型方案；更精细的音素驱动需另定接口。动作与表情增强为前端表现策略，不把用户 emotion 字段直接作为自动识别结果。

### 4.3 特殊分支

202 时进入待审批状态，无音频；批准或拒绝后调用 resume，当前只返回文字。音频生成失败可能发生在对话已保存之后，先查历史，不自动重发。签名 URL 过期与文件不存在统一按 404 处理；现有接口没有独立重签或只重合成端点。此能力如需增加，应单独设计归属校验、幂等键和内容来源。

# 5 用户端页面与状态设计

### 5.1 页面组织

以现有数字人主界面为核心，补充清晰的字幕、输入与播放控制区域。自评、活动、日记和资源以独立入口进入，避免交流界面承载所有表单。以下为前端完善建议，具体视觉样式和位置沿用实际用户端。

| 区域或页面 | 主要内容 | 交互要求 |
| --- | --- | --- |
| 数字人交流 | 形象 字幕 输入 播放状态 | 等待可见 避免重复发送 |
| 待确认事项 | 工具名称 说明 批准或拒绝 | 用户明确选择后执行 |
| 心理自评 | 量表介绍 逐题作答 结果 | 题目来源统一 保留未完成答案 |
| 健康活动 | 建议 呼吸练习 完成与延期 | 前端计时 服务端保存状态 |
| 个人记录 | 日记 自评 历史与资料 | 区分查看 修改与删除 |
| 知识与音乐 | 分类 详情 播放器 | 音乐和数字人声音协调 |

### 5.2 数字人状态控制

| 状态 | 触发条件 | 前端处理与转移 |
| --- | --- | --- |
| 就绪 | 已登录且无当前任务 | 允许输入与发送 |
| 生成中 | 请求已发出 | 展示等待 防止重复提交 |
| 待审批 | 收到 202 | 不播放 等待批准或拒绝 |
| 音频准备 | 收到 200 | 展示字幕 加载解码音频 |
| 说话中 | 音频实际开始 | 驱动口型 允许停止播放 |
| 播放受阻或失败 | 权限 解码或下载异常 | 保留文字 提示可操作原因 |
| 结束 | 播放结束 停播或离开 | 停止口型 释放资源 返回就绪 |

### 5.3 并发与生命周期

建议以一轮交流标识绑定文字、音频和模型状态；过期轮次的异步回调不得覆盖当前轮次。切换账号与页面离开时停止播放器、断开音频分析、释放临时对象并终止活动轮询。停止播放后的晚到响应不能自动再次发声。

活动轮询按服务端间隔串行执行，前台默认 20 秒，页面隐藏暂停，401 停止。用户端应提供字幕、显式播放按钮和适配触控的操作区域，并在 Windows 与 Android 实机验证。

# 6 服务端与数据设计

### 6.1 服务端实施内容

保留现有 HTTP 路由和认证中间件，使用应用服务统一执行业务，避免前端承担计分或归属判断。对话通过 Agent 编排结合历史、记忆、画像与 RAG；音频合成由宿主语音服务衔接。新增能力优先通过既有协议扩展，涉及响应结构变化时记录兼容策略。

### 6.2 核心数据关系

![核心业务数据关系](assets/data_relationship.png)

图示为逻辑关系，不替代数据库 DDL。个人资源由认证用户归属约束；会话关联消息与后置审计；评估关联答案及活动建议；音频为按有效期管理的输出文件，不作为永久历史音频资源。

### 6.3 一致性与恢复

自评与两条建议保持同一事务保存。建议完成、忽略和延期遵循既有状态约束；日记保存与建议完成是分离请求，客户端按顺序执行并分别处理失败。Checkpoint 按用户归属、有效期与消费状态管理，重复恢复应测试竞争行为。

数据库升级先备份、对比实际 DDL，再执行需要的增量迁移；不在已有库运行 init.sql。量表题号、选项分值与历史评估关联保持一致，不能使用种子脚本随意覆盖线上量表编号。向量模型或维度调整时采用独立索引重建与切换方案，不直接混用旧向量。

### 6.4 接口交付

将音频正常与暂停两种响应作为显式分支处理：正常字段为 camelCase，暂停协议沿用 snake_case。现有 @serverrs/sdk 未见音频发送方法，本轮可直接按 HTTP 接入；如补 SDK 方法，需同步请求类型、联合响应类型、错误处理和调用示例。

# 7 安全与运行部署

### 7.1 访问与数据保护

前端使用有效访问凭证，个人接口按认证身份约束数据，管理接口叠加管理员角色校验。服务端不接受通过前端传 userId 绕过归属。测试覆盖无凭证、无效凭证、普通用户调用管理接口及跨用户读取和修改。

生产部署使用独立强密钥、受限数据库账号和明确的允许来源。日志不记录访问令牌、密码、音频签名 URL 和完整敏感正文。音频签名 URL 具有访问能力，应短期使用，避免持久化或进入分析统计。

### 7.2 部署拓扑

用户终端通过可达域名访问前端和 API；同域反向代理可减少跨域配置差异。服务端通过内部网络访问 MySQL、Qdrant、模型服务和文件目录。TTS 若采用外部供应商，需独立核对网络、凭证、资源授权和使用成本。

| 部署项 | 现有基础 | 本轮落地要求 |
| --- | --- | --- |
| 应用与管理页 | Rust 托管或独立 Nginx | 确认同域路径与刷新行为 |
| 离线 Windows | Docker Desktop Linux 容器 | 验证完整导入 启动 停止与重启 |
| 语音 | TTS Provider 与 ffmpeg | 启用检查 输出规格及清理验证 |
| 音频公开地址 | public_url_base | 真实终端可达 HTTPS 一致 |
| 持久化 | MySQL 向量与对象数据 | 运行数据置于受控持久化目录 |
| 备份与恢复 | 现有数据库和文件 | 制定频率 保留期并完成恢复演练 |

### 7.3 运行观测

除 /health 外，增加或完善依赖连通性、模型调用失败、TTS 耗时、音频下载失败、风险审计积压和磁盘余量的观测。这里列为实施要求，不将健康端点等同于完整依赖监控。

资源与性能通过目标设备采样确定。离线文档中的内存建议用于部署起点，不能当作容量保证。若配置仍依赖外部语音服务，离线验收应分别记录文本可用和语音不可用的原因，不能合并为整体语音离线可用。

新增语音输入、改用渲染引擎、增加音素时间轴、接入推送及新增量表均需评估接口、数据、终端和验收影响，再调整计划。版本变更同步修订说明书，避免交付页面与文字说明不一致。

# 9 测试验收与交付

### 9.1 核心验收用例

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| A01 | 登录与权限 | 普通用户无管理权限 他人记录不能访问 |
| A02 | 数字人正常交流 | 真实服务返回文字与音频 播放驱动对应轮次 |
| A03 | 播放异常与停播 | 保留字幕 口型停止 晚到回调不重新发声 |
| A04 | 地址过期与不可达 | 明确提示 不自动重发造成重复对话 |
| A05 | 工具审批 | 202 无音频 用户决策后恢复 查询不执行 |

### 9.2 性能记录与质量门槛

分别记录请求至回复完成、TTS 处理、音频下载、解码至实际播放的耗时，按设备和网络统计 P50、P95、失败率及内存变化。先形成实测基线，再由项目组确认可接受阈值和并发目标；不以未经验证的毫秒数或并发数作为现状。

发布前核心任务全部通过，阻断登录、泄露他人信息、造成数据错误或使主要链路不可用的缺陷清零。普通缺陷逐项记录影响及处理安排。代码中忽略的依赖型测试、未执行的实机用例不得计为通过。

# 10 风险与后续演进

### 10.1 风险及应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 外部 TTS 不可用 | 有文本但不能完成声音链路 | 分离文字与语音错误 明确依赖 |
| URL 指向本机或过期 | 终端无法下载音频 | 真实终端验证公开地址与有效期 |
| 播放与数字人状态失配 | 口型漂移 停播后仍动作 | 统一时钟 轮次绑定与资源释放 |
| 写入超时后重复提交 | 重复对话 自评或日记 | 先读确认 后续评估幂等机制 |
| 历史文档与实现不符 | 测试范围及用户理解错误 | 维护功能状态和验收追溯表 |
| 旧库误用初始化脚本 | 业务数据丢失 | 增量迁移前备份及隔离验证 |
| 模型与设备性能差异 | 等待过长或资源不足 | 按目标硬件采样 调整模型配置 |
| 识别结果被过度解释 | 界面产生错误结论 | 区分自评 审计 置信度和人工复核 |

### 10.2 后续演进顺序

首先补充按既有回复重新生成音频或重新签发地址的专用能力，前提是设计本人归属校验、内容一致性、幂等和成本限制。其次评估审批恢复后语音输出，使正常与恢复链路体验一致。

在基础链路稳定后，再评估音素时间标记、表情动作协同、语音输入和更低延迟的分段合成。任何流式协议需要重新设计分片顺序、取消、重连及字幕同步，不能直接把现有完整文件接口当作流式协议。

Fresh Context 与网页知识审核若恢复，先核对来源、发布审核、索引及聊天引用的完整链路，再调整开关和用户入口。系统通知与人工工作流应单独设计权限、责任和状态，不从当前轮询或风险列表推导为已经具备。
